# 문서 생성 속도 — 지연 원인과 개선 방안

소스 수정 없이 참고할 수 있는 요약과, 추후 적용 시 고려할 수 있는 개선 아이디어를 정리했습니다.

---

## 1. 어디서 시간이 걸리는지

전체 흐름은 **2단계**입니다.

| 단계 | 내용 | 대략적인 지연 |
|------|------|----------------|
| **1단계** | 원시 md → **정리 md** (LLM 1회, 테스트케이스/개발피처는 N회차 없음) | 입력·출력 길이에 비례 |
| **2단계** | 정리 md + **HTML 템플릿** → **완성 HTML** (LLM 1회) | **가장 큰 구간** |

**HTML 만드는 단계가 주요 딜레이**인 이유:

1. **입력이 큼**  
   - 시스템 프롬프트: **전체 HTML 템플릿**(테스트케이스/개발피처는 문서 구조+스타일 전체) + 출력 규칙.  
   - 유저 프롬프트: **[정리된 보고 내용]** 전체.  
   → 토큰 수가 많아지면 처리 시간이 길어짐.

2. **출력이 큼**  
   - 한 번에 **전체 HTML 문서**를 생성.  
   - `max_completion_tokens` 상한이 크면(예: 16384) 모델이 긴 출력을 끝까지 생성할 때까지 대기.

3. **모델 특성**  
   - 같은 토큰 수라도 모델/옵션(reasoning 등)에 따라 체감 속도가 다름.

---

## 2. 소스 수정 없이 할 수 있는 것

- **입력 문서 길이 줄이기**  
  원시 문서(페이지 수, 분량)가 크면 정리 md·HTML 모두 길어져 두 단계 모두 느려짐.  
  테스트 시에는 짧은 PDF/PPTX로 구간별 체감 시간을 비교해 보면 좋음.

- **모델 선택**  
  - HTML 단계만이라도 **응답이 빠른 모델**(예: gpt-4o-mini, Claude Haiku 등)을 쓰면 체감 속도가 빨라질 수 있음.  
  - 현재는 1·2단계 모두 같은 모델을 쓰므로, 설정에서 더 빠른 모델을 선택하면 전체가 빨라짐 (품질 트레이드오프는 있음).

- **고품질 모드 비사용**  
  경영진/실무는 고품질 시 N회차 호출로 시간이 늘어남.  
  테스트케이스/개발피처는 고품질 없이 1회 호출만 하므로 이 부분은 이미 상대적으로 가벼움.

---

## 3. 추후 코드로 개선할 때 고려할 수 있는 것

(아래는 “이렇게 하면 더 빨라질 수 있다” 수준의 아이디어이며, 지금 저장소에는 반영하지 않음. **단, 3.1+3.2는 HTML 단계에 적용 완료(빠른 모델 고정+스트리밍).**)

### 3.1 HTML 단계만 더 빠른/작은 모델 사용

- 1단계(정리 md)는 현재 모델, **2단계(md→HTML)만** 더 빠른 모델로 호출.
- 품질은 1단계에 많이 의존하고, HTML은 “형식 맞추기”에 가깝다면 수용 가능할 수 있음.
- 구현 시: 2단계 호출부에서만 다른 `selection`/모델을 쓰거나, “2단계용 모델” 설정을 추가.

### 3.2 HTML 단계 스트리밍

- API가 스트리밍을 지원하면, **HTML 출력을 스트리밍**으로 받아서 화면에 순차 렌더링.
- “전체 생성이 끝날 때까지 한 번에 기다리기”보다 체감 대기 시간이 줄어듦.
- 구현 시: `generateHtmlFromMarkdownClient`(또는 내부 `callLlm`)에서 스트리밍 응답을 구독하고, chunk 단위로 HTML을 이어 붙여 뷰어에 전달.

### 3.3 템플릿을 컨텍스트에서 줄이기

- 현재: **전체 HTML**(헤더, `<style>`, 본문 골격)을 시스템/유저 프롬프트에 넣음.
- 개선 아이디어:  
  - “클래스명·섹션 구조·스타일 규칙”만 짧은 지시문으로 주고,  
  - “위 규칙과 [정리된 보고 내용]으로 완성 HTML을 만들어라”처럼 요청해 **입력 토큰**을 줄임.
- 장점: API 처리 시간·비용 감소.  
- 단점: 출력 형식이 달라질 수 있어, 검증·튜닝이 필요함.

### 3.4 테스트케이스/개발피처도 “스켈레톤 + 채우기” 방식

- 경영진/실무 **default**는 이미 “고정 HTML 스켈레톤 + 변수 채우기” 방식(C방식)으로, **전체 HTML을 LLM이 한 번에 생성하지 않음** → 상대적으로 빠름.
- 테스트케이스/개발피처도  
  - **고정된 HTML 골격**(테이블 헤더, 섹션 구조)을 두고,  
  - LLM은 **“표의 각 행 데이터만”** 또는 **“섹션별 내용만”** 생성하게 하면,  
  - “긴 HTML 한 덩어리” 생성보다 토큰 수·시간을 줄일 수 있음.
- 구현 난이도는 높음: 테이블 행/셀 구조를 파싱해 DOM에 넣는 로직이 필요.

### 3.5 2단계 출력 상한 조정

- 현재 2단계도 `REFINED_MD_MAX_TOKENS`(16384) 수준의 상한을 쓰는 경우가 있음.
- “실제로 필요한 HTML 길이”보다 크게 잡혀 있으면, 불필요하게 긴 생성까지 기다리게 될 수 있음.
- 문서 타입별로 **2단계만** 더 작은 `max_completion_tokens`를 두면, 최악의 대기 시간을 줄일 수 있음 (너무 작으면 잘림 주의).

### 3.6 캐싱

- **템플릿 내용**: API에서 한 번 불러온 뒤 메모리/세션에 캐시하면, 같은 세션에서 재생성 시 네트워크·파싱 비용 감소 (이미 일부 적용되어 있을 수 있음).
- **정리 md 재사용**: 이미 구현됨. “HTML 형식만 바꿔서 다시 만들기” 시 정리 md는 재생성하지 않음.

---

## 4. 요약

- **주요 딜레이**: **정리 md → HTML** 만드는 2단계 (입력·출력이 크고, 한 번에 전체 HTML 생성).
- **지금 바로**: 짧은 문서로 테스트, 더 빠른 모델 선택, 고품질 모드 비사용으로 체감 속도 확인 가능.
- **추후 개선 시**: 2단계만 빠른 모델, 스트리밍, 템플릿 축약, 테스트케이스/개발피처도 스켈레톤+채우기, 2단계 max 토큰 조정 등을 검토할 수 있음.

이 문서는 `docs/10-report-generation-latency-ko.md` 로 두고, 구현 시 참고용으로만 사용하면 됩니다.
