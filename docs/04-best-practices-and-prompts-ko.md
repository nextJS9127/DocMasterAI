# DocMaster AI — 베스트 프랙티스 기획 및 프롬프트·결과 포맷 설계

## 1. 개요

### 1.1 목적

- 사용자가 **고민하지 않고** 메인 화면에서 **용도별 시나리오**를 골라 바로 사용할 수 있게 한다.
- 선택한 베스트 프랙티스에 따라 **기본 프롬프트**가 자동 반영되고, **생성 결과 문서의 포맷**이 용도에 맞게 고정된다.
- 기존 “경영진용/실무용 보고서”를 **한 축**으로 유지하면서, **개발 피쳐 정리**와 **품질관리용 테스트 케이스** 시나리오를 추가한다.

### 1.2 베스트 프랙티스 3종

| ID | 한글 제목 | 영문 제목 | 한 줄 설명 |
|----|-----------|-----------|------------|
| `report` | 기획서 기반 보고서 만들기 | Planning-based Report | 기획서·제안서 PDF/PPTX를 업로드하면 경영진용·실무용 보고서로 정리 |
| `features` | 기획서/첨부 기준 개발 피쳐 만들기 | Planning → Dev Features | 기획서·첨부 자료를 분석해 카테고리별 개발 피쳐·요건 목록 생성 |
| `testcases` | 품질관리 기준 테스트 케이스 만들기 | QA Test Cases | 문서를 바탕으로 영역별·단계별·예상 결과가 정의된 테스트 케이스 문서 생성 |

## 2. 메인 화면 UX 및 베스트 프랙티스 영역

### 2.1 배치

- **위치**: 메인 화면 **하단** (업로드 영역 바로 아래, idle 상태일 때 표시).
- **구성**: 가로 3열 카드. 각 카드 = 썸네일 + 제목 + 짧은 설명 + “이렇게 사용하세요” 한 줄.
- **동작**:
  - 카드 **클릭** → 해당 베스트 프랙티스가 **선택**됨.
  - 선택 시 **기본 프롬프트**가 해당 시나리오용으로 설정(설정 모달의 경영진용/실무용 또는 전용 프리셋에 반영).
  - 선택된 카드는 시각적으로 강조(테두리/배경).
  - **파일 업로드 → 추출 → Step 2**로 넘어갈 때, 선택된 베스트 프랙티스에 맞는 **보고 유형 + 출력 포맷**이 자동 적용.

### 2.2 썸네일 이미지 스펙

- **크기**: 카드 내 16:9 또는 4:3 비율, 최소 280×160 px.
- **스타일**: 일관된 톤(그라데이션·아이콘·최소한의 텍스트).
- **제안**:
  1. **기획서 기반 보고서**: 문서 → 요약/차트 아이콘, 색상 인디고/블루.
  2. **개발 피쳐**: 트리/리스트·카테고리 아이콘, 색상 에메랄드/티얼.
  3. **테스트 케이스**: 체크리스트·검증 아이콘, 색상 앰버/오렌지.
- **구현**: SVG 또는 정적 이미지(`public/best-practice-report.svg` 등)로 제공. 필요 시 LLM/이미지 툴로 동일 비율 썸네일 생성.

**썸네일 제작 가이드 (개발자용)**  
- 동일 비율(예: 320×180)로 3장 제작.  
- 배경: 그라데이션 또는 단색 + 흰색/연한 카드 영역.  
- 중앙에 Lucide/Feather 스타일 아이콘 1개 + 짧은 라벨(예: "보고서", "피쳐", "테스트").  
- 파일명: `best-practice-report.svg`, `best-practice-features.svg`, `best-practice-testcases.svg` → `docmaster-web/public/` 에 두고 카드에서 `img` 로 참조.

### 2.3 “이렇게 사용하세요” 문구 (예시)

| ID | 한글 | 영문 |
|----|------|------|
| `report` | 기획서 PDF/PPTX를 넣고, 경영진용 또는 실무용을 고른 뒤 [보고서 생성]을 누르세요. | Upload a planning doc (PDF/PPTX), choose Executive or Team, then click [Generate Report]. |
| `features` | 기획서나 요구사항 문서를 넣고 [생성]을 누르면 카테고리별 개발 피쳐 목록이 나옵니다. | Upload a planning or requirements doc, then generate to get a category-based feature list. |
| `testcases` | 기획서·명세서를 넣고 [생성]을 누르면 영역·단계·예상 결과가 있는 테스트 케이스가 나옵니다. | Upload a spec or planning doc, then generate to get test cases with area, step, and expected result. |

## 3. 베스트 프랙티스별 프롬프트·결과 포맷

### 3.1 `report` — 기획서 기반 보고서 만들기

- **현행과 동일**: 이미 “경영진용(Executive)” / “실무용(Team)” 두 가지 보고 유형과 여러 HTML 템플릿이 있음.
- **선택 시 적용**:
  - 기본 프롬프트: **경영진용** 또는 **실무용** 중 하나를 기본값으로 설정(예: 경영진용).
  - HTML 형식: **default** 또는 **phase1** 등 기획서에 맞는 템플릿을 기본 선택.
- **프롬프트**: 기존 `DEFAULT_PROMPT_EXECUTIVE_EDITABLE` / `DEFAULT_PROMPT_TEAM_EDITABLE` 유지. (이미 문서화됨.)
- **결과 포맷**: 기존과 동일 — ````markdown` 블록 + ````html` 블록, 템플릿 변수 `{{summary}}`, `{{chart_description}}`, `{{options_risk}}`, `{{action_item}}` 등 채워진 HTML.

**추가 조정 가능**:  
- “기획서 기반 보고서” 선택 시 설정에 “경영진용 기본” 또는 “실무용 기본” 옵션을 두고, 그에 따라 초기 `reportType`과 `templateId`만 바꿔 주면 됨.

---

### 3.2 `features` — 기획서/첨부 기준 개발 피쳐 만들기

**목적**: 기획서·요구사항 문서를 넣으면, **카테고리(도메인/모듈)별로** “무엇을 개발해야 하는지”를 정리한 문서를 생성한다.

#### 역할·입출력

- **역할**: 시니어 테크 리드/제품 기획자. 기획서와 첨부 자료에서 **기능·비기능 요건**을 추출하고, **카테고리**로 묶어 **개발 피쳐** 목록으로 구조화한다.
- **입력**: [원천 데이터] = PDF/PPTX에서 추출된 마크다운.
- **출력**: 카테고리 → 피쳐 목록 → 각 피쳐별 설명·우선순위·수용 기준(선택).

#### 기본 프롬프트 (편집 가능 블록) — 한글 초안

```text
# Role & Objective
당신은 15년 차 테크 리드이자 제품 기획자입니다.
[원천 데이터]를 분석하여, 개발팀이 바로 작업 목록으로 쓸 수 있는 **카테고리별 개발 피쳐(기능·요건) 문서**를 작성합니다.

# Input Data 규칙
- [원천 데이터]: PDF/PPTX에서 추출·정제된 마크다운입니다. [[TABLE]]/[[DIAGRAM]] 블록이 있으면 표·다이어그램 설명으로 반영하세요.

# Core Rules
1. 원천 데이터에 없는 기능·요건을 창작하지 마세요. 확인이 필요한 부분은 [확인 필요]로 표시하세요.
2. 카테고리는 원천 데이터의 구조(챕터·섹션·도메인)를 반영하거나, 논리적으로 묶을 수 있는 단위(예: 회원·주문·결제·관리자)로 나누세요.
3. 각 피쳐는 한 문장 이상의 설명, 우선순위(필수/권장/선택), 필요 시 수용 기준(Acceptance Criteria) 1~3줄을 포함하세요.

# 필수 출력 구조 (아래 순서와 헤딩을 준수)
1. **문서 개요**: 문서 목적, 원천 문서 성격, 대상 독자(개발·기획·QA 등).
2. **카테고리 목록**: 카테고리 ID·이름·한 줄 설명.
3. **카테고리별 개발 피쳐**: 각 카테고리마다
   - 카테고리명 (ID)
   - 피쳐 목록 (테이블 또는 리스트)
     - 피쳐 ID, 제목, 설명, 우선순위, 수용 기준(선택)
4. **의존성·참고**: 카테고리/피쳐 간 선행 조건·참고 문서가 있으면 간단히 명시.

# 출력 형식
1) 정리된 내용(마크다운): ```markdown ... ``` 블록에 위 구조대로 작성.
2) 완성 HTML: ```html ... ``` 블록에, 위키 스타일 또는 기획서 스타일의 HTML로 동일 내용을 출력. 표는 <table>로, 카테고리별 섹션은 <h2>/<h3>로 구분.
```

- **영문 버전**: 동일 구조로 Role/Input/Core Rules/필수 출력 구조를 영문으로 작성해 두면 됨.

#### 결과 문서 포맷 (정의)

- **마크다운**:
  - `# 문서 개요` → 목적, 원천 문서, 대상 독자.
  - `# 카테고리 목록` → 표 또는 리스트: ID, 카테고리명, 한 줄 설명.
  - `## [카테고리명]` (반복) → 해당 카테고리 내 **피쳐 테이블**: 피쳐 ID, 제목, 설명, 우선순위, 수용 기준.
  - `# 의존성·참고` (선택).
- **HTML**: 위 구조를 그대로 옮긴 단일 HTML. 표·섹션 구분 명확. (기존 위키 스타일 가이드 또는 phase1 스타일 재사용 가능.)

#### LLM 클라이언트 연동

- `reportType` 확장: `'executive' | 'team' | 'features'` 또는 별도 플래그 `outputMode: 'report' | 'features' | 'testcases'` 도입.
- `features` 선택 시: 위 **편집 가능 프롬프트**를 시스템 프롬프트로 사용하고, HTML 고정 규칙은 “위키 또는 기획서 스타일, 표·섹션 구조 유지”만 주면 됨.

---

### 3.3 `testcases` — 품질관리 기준 테스트 케이스 만들기

**목적**: 기획서·명세서를 넣으면, **품질관리 인원**이 그대로 사용할 수 있는 **테스트 케이스 문서**를 생성한다.  
- **영역(모듈/기능)별** 구분  
- **단계(스텝)** 별로 “무엇을 하는지”  
- **예상 결과**가 명시된 형식

#### 역할·입출력

- **역할**: 시니어 QA 리드. [원천 데이터]에서 **기능·플로우·비즈니스 룰**을 읽어, **영역 → 단계 → 조치 → 예상 결과** 구조의 테스트 케이스를 작성한다.
- **입력**: [원천 데이터] = 추출 마크다운.
- **출력**: 테스트 케이스 문서 (영역별, 단계별, 예상 결과 포함).

#### 기본 프롬프트 (편집 가능 블록) — 한글 초안

```text
# Role & Objective
당신은 15년 차 QA 리드입니다.
[원천 데이터]를 분석하여, 품질관리 인원이 그대로 실행할 수 있는 **테스트 케이스 문서**를 작성합니다.
각 케이스는 **영역(모듈/기능)** · **단계(스텝)** · **조치(무엇을 하는지)** · **예상 결과**를 포함해야 합니다.

# Input Data 규칙
- [원천 데이터]: PDF/PPTX에서 추출된 마크다운입니다. [[TABLE]]/[[DIAGRAM]]이 있으면 표·흐름으로 반영하세요.

# Core Rules
1. 원천 데이터에 없는 동작·결과를 만들지 마세요. 불명확한 부분은 [확인 필요]로 표시하세요.
2. 영역은 원천 문서의 기능/모듈/화면 단위로 나누세요 (예: 로그인, 회원가입, 주문 생성, 결제).
3. 각 테스트 케이스는 실행 가능한 단위로 나누고, 단계(Step)는 1, 2, 3…으로 번호를 부여하세요.
4. 예상 결과는 구체적으로 작성하세요 (예: “로그인 성공 시 대시보드로 이동”이 아닌 “URL이 /dashboard로 변경되고 사용자명이 상단에 표시됨”).

# 필수 출력 구조 (아래 순서와 헤딩 준수)
1. **문서 개요**: 테스트 대상 문서 요약, 대상 영역, 작성 기준일.
2. **테스트 케이스 목록(요약)**: 영역별 케이스 수, 우선순위 등 요약 표.
3. **영역별 테스트 케이스**: 각 영역마다
   - ## [영역명] (예: 로그인, 회원가입)
   - 테이블 또는 리스트:
     - 케이스 ID, 케이스명, 전제조건, 단계(Step), 조치(행동), 예상 결과, 비고
   - 단계는 1, 2, 3…으로 구체적 행동 단위로 나열.
4. **부록**: 용어 정리, 참고 화면/문서 (선택).

# 출력 형식
1) 정리된 내용(마크다운): ```markdown ... ``` 블록에 위 구조대로 작성.
2) 완성 HTML: ```html ... ``` 블록에, 표(<table>) 중심의 테스트 케이스 HTML. 영역은 <h2>, 케이스는 표로 표시.
```

- **영문 버전**: 동일 구조를 영문으로 작성.

#### 결과 문서 포맷 (정의)

- **마크다운**:
  - `# 문서 개요` → 테스트 대상, 대상 영역, 작성 기준일.
  - `# 테스트 케이스 목록(요약)` → 영역별 케이스 수 등 요약 표.
  - `## [영역명]` (반복) → 테이블: 케이스 ID, 케이스명, 전제조건, 단계, 조치, 예상 결과, 비고.
  - 단계(Step) 컬럼에는 “1. 로그인 화면 접속”, “2. ID/비밀번호 입력”처럼 구체적 행동 나열.
- **HTML**: 위 표 구조를 `<table>`로 옮긴 단일 HTML. 기존 위키 스타일 또는 단순 테이블 스타일 재사용.

#### LLM 클라이언트 연동

- `testcases` 선택 시: 위 **편집 가능 프롬프트**를 시스템 프롬프트로 사용.
- HTML 고정 규칙: “테스트 케이스 표 구조 유지, 영역별 <h2>, 표로 출력”.

## 4. 데이터·설정 매핑

### 4.1 베스트 프랙티스 → 프롬프트·출력

| bestPracticeId | 기본 reportType | 기본 templateId | 전용 프롬프트 키 (제안) |
|----------------|-----------------|----------------|--------------------------|
| `report`       | executive       | default 또는 phase1 | 기존 경영진용/실무용 |
| `features`     | (N/A 또는 team) | wiki 또는 phase1    | docmaster_promptFeaturesEditable |
| `testcases`   | (N/A 또는 team) | wiki 또는 전용 테스트 케이스 템플릿 | docmaster_promptTestcasesEditable |

- **선택 시 동작**:
  1. 사용자가 카드 클릭 → `selectedBestPracticeId` 저장 (예: localStorage `docmaster_bestPractice`).
  2. Step 2 진입 시:
     - `report` → 기존처럼 `reportType` + `templateId` 선택 UI 유지, 기본값만 설정.
     - `features` → “개발 피쳐” 전용 프롬프트 로드, 출력은 “카테고리별 피쳐” 포맷.
     - `testcases` → “테스트 케이스” 전용 프롬프트 로드, 출력은 “영역·단계·예상 결과” 포맷.
  3. 설정 모달에서는 “경영진용 / 실무용” 탭에 더해 “개발 피쳐 / 테스트 케이스” 탭을 두어 해당 프롬프트를 편집 가능하게 할 수 있음.

### 4.2 출력 포맷 공통 규칙

- 모든 시나리오에서 **1) 정리된 마크다운 블록**, **2) 완성 HTML 블록** 순서로 LLM 출력을 유지하면, 기존 파싱 로직(````markdown` / ````html` 추출)을 그대로 재사용할 수 있음.
- `features`·`testcases`용 HTML은 기존 `WIKI_STYLE_GUIDE` 또는 단순 테이블 스타일로 통일하면 구현 부담을 줄일 수 있음.

## 6. 요약

| 항목 | 내용 |
|------|------|
| **베스트 프랙티스** | ① 기획서 기반 보고서 ② 개발 피쳐 ③ 테스트 케이스 — 메인 하단 3열 카드, 썸네일·설명·사용법 포함. |
| **선택 시** | 해당 시나리오의 기본 프롬프트 반영, Step 2에서 보고 유형/출력 포맷 자동 또는 가이드. |
| **프롬프트** | `report`는 기존 경영진/실무용 유지; `features`·`testcases`는 위 문단의 역할·규칙·필수 출력 구조로 신규 정의. |
| **결과 포맷** | `report`는 기존 HTML 템플릿; `features`는 카테고리→피쳐 목록(표); `testcases`는 영역→단계→조치→예상 결과(표). |
| **다음 단계** | 썸네일 제작, 프론트 카드 컴포넌트 및 선택 상태 연동, LLM 클라이언트에 `features`/`testcases` 분기 및 전용 프롬프트 적용. |

이 문서를 기준으로 프롬프트 문구를 세밀하게 다듬고, 실제 출력 샘플을 몇 차례 생성해 보면서 “카테고리별 피쳐”와 “영역·단계·예상 결과” 포맷을 조정하면 된다.
